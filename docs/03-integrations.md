# Как связываются отдельные приложения

## Границы ответственности

SruNal отвечает за ленту, комментарии, сообщества, профиль, основную вкладку календаря и каталог четырёх приложений. Отдельные приложения управляют своими данными и бизнес-правилами. Интеграция вызывает конкретное действие с разрешения пользователя; для личного общения профиль открывает Telegram.

Отдельность приложений означает самостоятельные пользовательские сценарии и границы данных. Она не обязывает создавать новый микросервис или базу для каждой карточки каталога.

| Владелец | Источник истины |
| --- | --- |
| SruNal | Профиль, пост, комментарий, просмотр, подписка, сообщество, блокировка, каталог и разрешения на связи |
| Docgen | Заказ, цена, оплата, генерация, результат, доступность файла |
| SruDay | Событие, повторения, календарная группа, настройки доступности |
| SruPulse | Статус свободного времени, время окончания, аудитория, отклик |
| SruNotes | Текст заметки, владелец и разрешения на просмотр |
| SruSplit | Группа расходов, участники, суммы, плательщики, доли и балансы |

Связанный экран показывает данные владельца или явно отмеченную копию. Отдельно проверяем, какие данные можно кэшировать и когда они устаревают.

## Подключение существующих проектов

### Шаг 1: запуск из каталога

Существующие Docgen и SruDay могут работать самостоятельно, но в SruNal каталог содержит только Docgen, SruNotes, SruSplit и SruPulse. Календарь открывается отдельной основной вкладкой `/calendar`. Дальнейшие шаги описывают границы адаптации, а не перечень ещё не созданных каталогов; текущий статус находится в [README](README.md).

В каталоге приложения достаточно стабильного идентификатора, названия, описания, иконки и проверенного адреса запуска. Адреса берём из конфигурации владельца, а не из введённой пользователем произвольной ссылки.

Используем [прямые ссылки Telegram и `startapp`](https://core.telegram.org/bots/webapps#direct-link-mini-apps) для перехода в поддерживаемые разделы. Параметр запуска является маршрутом или ссылкой на запрос, но не доказательством права на объект.

Так пользователь может открыть существующие сервисы из соцсети SruNal. Это промежуточный этап подключения Docgen и SruDay: общий экран приложения внутри SruNal и обмен данными ещё требуют адаптации.

### Шаг 2: отдельные пространства внутри оболочки

Четыре приложения открываются в собственных пространствах: `/apps/doc`, `/apps/pulse`, `/apps/notes`, `/apps/split`. Основные разделы SruNal: `/feed`, `/calendar` и `/profile`; `/people/{id}` открывает публичный профиль, `/posts/{id}` публикацию с комментариями. Старый `/apps/day` перенаправляется в календарь. Внутреннего мессенджера нет.

Для существующих фронтендов потребуется проверить базовые пути, абсолютные ссылки, загрузку ресурсов, обработчики Telegram SDK и авторизацию. Простое перемещение сборки в подпапку не гарантирует работоспособности.

Предпочтительный подход для начала: обычные React-модули с отдельными маршрутами и подключением к API владельца. Существующие проекты переносятся или адаптируются постепенно. iframe и платформа произвольных плагинов не входят в первую реализацию.

Каждое приложение имеет собственные папки `web/src/apps/<id>` и `backend/internal/apps/<id>`. Клиенты существующих сервисов принадлежат `apps/doc` и `apps/day`; сценарии между приложениями находятся в `backend/internal/integration` и обращаются к публичным методам владельцев. Правила и пофайловый пример находятся в [структуре модулей](11-project-layout.md).

### Шаг 3: действия между приложениями

Добавляем одну полезную связь за раз. Для SruNotes первой связью становится публикация карточки заметки в SruNal с проверкой доступа. Для существующих проектов начинаем с **Docgen → создать дедлайн в SruDay**. Поделиться файлом и связать социальные встречи можно после проверки доступа к файлам и событийной модели.

## Первые связи

| Откуда → куда | Действие | Что передаётся | Что подтверждает пользователь |
| --- | --- | --- | --- |
| Docgen → SruDay | Привязать работу к дедлайну | Название, выбранная дата, ссылка на свой заказ | Дату, текст и создание события |
| SruNal → SruDay | Добавить встречу из поста | Название, время, место, ссылка на исходный пост | Создание личной копии события |
| SruDay → SruNal | Обсудить встречу | Выбранные поля события и получатели | Какие выбранные поля попадут в публикацию |
| Docgen → SruNal | Поделиться материалом | Только выбранный результат или ссылка с правами | Получателей и доступное содержимое |
| SruNotes → SruNal | Поделиться заметкой | Карточка выбранной заметки и разрешённая аудитория | Получателей доступа на чтение и место отправки |
| SruPulse → SruDay | Сохранить согласованную встречу | Название и время, без списка получателей | Создание личного события |
| SruPulse → SruNal | Обсудить отклик | Статус, автор, откликнувшийся пользователь | Открытие публичного профиля и связи в Telegram |
| SruSplit → SruNal | Обсудить расчёт | Карточка группы расходов с проверкой прав | Какие получатели смогут увидеть расчёт |

Начальная связь «документ к дедлайну» может сохранять только ссылку на заказ. Она не должна обещать длительное хранение файла: в Docgen документация сейчас указывает доступность результата в Mini App 30 дней.

## Выполнение действия

1. Пользователь нажимает действие в исходном приложении.
2. Сервер проверяет его право на исходный объект.
3. Открывается целевое приложение с заполненным черновиком и указанием источника.
4. Пользователь проверяет поля, получателей и подтверждает.
5. Целевое приложение сохраняет результат по своим правилам и возвращает ссылку.

Открытие уже существующего профиля или карточки заметки не создаёт новый объект. Отправка карточки, предоставление доступа и создание события являются изменяющими действиями и проходят соответствующие проверки.

Повторное нажатие или повтор HTTP-запроса не создают дубль: запрос имеет идентификатор, а целевой сервис запоминает результат его выполнения. Подтверждение привязывается к конкретному содержимому и аудитории; изменение этих данных требует новой проверки пользователем.

При ошибке исходный объект остаётся на месте. Показываем, что именно не выполнено, и разрешаем повторить действие. Очередь событий и универсальный конструктор автоматизаций для первых связей не нужны.

## Вход и привязка аккаунтов

Личность подтверждается на сервере через `initData`. Telegram описывает проверку подписи и свежести `auth_date` в [документации валидации](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). `initDataUnsafe`, имя пользователя и параметры ссылки не являются основанием для доступа.

У Docgen сейчас проверяется `initData` в запросах, а у SruDay после Telegram-входа выдаётся собственная сессия. Это разные механизмы. Токены сессий и внутренние `user_id` одного приложения нельзя передавать другому как общую авторизацию.

Если приложения открыты под разными ботами, HMAC-проверка привязана к токену соответствующего бота. На этапе отдельных запусков каждое приложение выполняет свой вход. Для будущего общего запуска потребуется явный доверенный механизм: например, проверяемый целевым сервисом краткоживущий одноразовый код от сервера SruNal. Его привязывают к пользователю, целевому приложению и действию; обмен происходит на сервере. Этот механизм ещё требуется реализовать и проверить.

Telegram также поддерживает [проверку для третьей стороны без передачи токена бота](https://core.telegram.org/bots/webapps#validating-data-for-third-party-use), но текущие сервисы не следует считать уже совместимыми с ней.

Для связи аккаунтов используем подтверждённый числовой Telegram ID и явное сопоставление с локальными аккаунтами. Смена username не создаёт нового пользователя. Перенос старых аккаунтов, не связанных с Telegram, требует отдельного подтверждения владения.

## Разрешения и приватность

Связь между приложениями выключена до первого использования. Для неё показываем цель, доступные данные и возможность отключения. Разовое действие не даёт постоянный доступ ко всему приложению.

- Публикация статуса SruPulse не открывает названия событий календаря.
- Участие в сообществе не добавляет всех участников в друзья SruDay.
- Права оператора Docgen не дают доступ к чужим заметкам, календарю и расходам.
- Заметки SruNotes остаются приватными до явного предоставления доступа; пересланная карточка не расширяет аудиторию.
- Суммы SruSplit не появляются в общей ленте или профиле. Обсуждение в Telegram не добавляет людей в группу расходов.
- Цена, факт оплаты, ФИО титульного листа и служебные логи не входят в карточку общего материала.
- Файл доступен через серверную проверку прав; для скачивания можно выдавать короткоживущую ссылку. Ссылка на приватный заказ сама по себе не открывает заказ получателю.

Отключение связи запрещает новые обращения и отзывает выданный доступ, но не удаляет автоматически уже созданное личное событие или скачанный получателем файл. Это объясняется до отправки. Для публикации файла нужен отдельный выбор: дать управляемый доступ или создать отдельную копию; первая версия не должна молча делать второе.

Начальная интеграция календаря односторонняя: она создаёт копию события с источником. Последующие правки исходного поста не меняют расписание автоматически. Удалённый или недоступный источник отображается соответствующим состоянием, личная копия сохраняется.

## Уведомления

Основной внешний канал SruNal: сообщения в личном чате Telegram-бота. Они сообщают о поддерживаемых событиях SruPulse, доступе к заметке и изменениях расходов. Уведомлений внутреннего мессенджера нет. Бот даёт кнопку перехода к нужному объекту, а не переносит в уведомление всё приватное содержимое.

API сохраняет задание вместе с изменением в PostgreSQL. Отдельный worker отправляет сообщение через Bot API с проверкой прав, настройками mute и повторами после временных ошибок. Подробности находятся в [архитектуре уведомлений](08-bot-notifications.md).

Docgen и SruDay на этапе независимых запусков сохраняют существующих ботов. Перенос их событий в бота SruNal выполняется с единым владельцем доставки. Один и тот же токен бота не используется одновременно независимыми webhook и long polling обработчиками.

Для сообщений от бота проверяется разрешение пользователя; Mini App поддерживает [`requestWriteAccess`](https://core.telegram.org/bots/webapps#initializing-mini-apps). Открытое приложение не гарантирует право бота писать в личные сообщения. Заблокированный бот не должен приводить к потере события внутри приложения.

Уведомления по умолчанию не включают текст приватного сообщения, содержимое заметки и суммы расходов. Диалог или категорию можно заглушить. Пересланная кнопка не даёт права на исходный объект.

## Оплата Docgen

В существующем Docgen описан сценарий Kaspi QR с подтверждением оператором. Это описание текущего продукта, а не утверждённая схема оплаты нового super app.

По [правилам Telegram для цифровых товаров и услуг](https://core.telegram.org/bots/payments-stars) продажи внутри ботов и Mini Apps должны использовать Telegram Stars. Для платных цифровых документов планируем соответствующий сценарий; публикация платного раздела требует его проработки. В текущей задаче существующие платежи не меняются.

Факт оплаты подтверждается серверным событием платёжной системы. Закрытие платёжного окна или нажатие «Я оплатил» не означает успешной оплаты. Старые оплаченные заказы и файлы сохраняют доступность при миграции.

## Техническая основа

Для SruNal выбраны React 19 + Vite + TypeScript, Tailwind 4 и UI/UX существующего DocGen, Go и PostgreSQL 18. Docgen является пользовательским названием подключённого проекта DocGen, его исходная папка и внутренние контракты не переименовываются автоматически.

Социальная основа, SruNotes, SruSplit и SruPulse работают в одном модульном Go-приложении с общей новой БД. Из одного модуля запускаются API и worker уведомлений, миграции применяются отдельной командой. Docgen и SruDay продолжают обслуживать свои данные через собственные API и существующие базы.

Конкретные границы и структура описаны в [архитектуре](06-architecture.md), схема хранения в [модели данных](07-data-model.md). Приватные поля шифруются ключами вне БД, права проверяются до выдачи и расшифровки согласно [модели безопасности](10-security.md).

Начальный объём не требует Kubernetes, брокера сообщений, системы плагинов, общего кошелька или обязательного переноса всех баз. Хранилище файлов подключается при появлении конкретного сценария вложений, с учётом текущего хранения результатов Docgen и скриншотов SruDay.
