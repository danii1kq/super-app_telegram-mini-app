# PostgreSQL и модель данных

## Выбор БД

Для новых данных SruNal выбираем **PostgreSQL 18**. Связи между людьми, сообществами, заметками и расходами выражаются внешними ключами. Транзакции позволяют сохранять изменение вместе с уведомлением и менять расход вместе со всеми долями. База также хранит отзывные сессии и очередь отправки в Telegram.

Одна новая база `srunal` обслуживает социальную основу, SruPulse, SruNotes и SruSplit. Таблицы разделены префиксами и владельцами в коде. Старые базы проекта DocGen, который представлен как Docgen, и SruDay сохраняются отдельно. Для них в SruNal хранятся только подтверждённые привязки аккаунтов и запросы интеграций.

Это логическая схема. Фактический порядок изменений зафиксирован в `db/migrations/`; миграции применяет отдельная команда до запуска совместимой версии сервера.

## Типы и общие правила

- Первичные ключи: `bigint generated always as identity`. В API идентификаторы передаются строками, чтобы не зависеть от безопасного диапазона JavaScript Number.
- Telegram ID: целое число внутри Go, зашифрованное значение в БД. Уникальный HMAC-индекс используется для поиска пользователя; обычный SHA от числового ID не применяется. Username является изменяемым полем.
- Моменты времени: `timestamptz`, обмен по RFC 3339. IANA timezone хранится отдельно в настройках пользователя; язык Telegram не определяет часовой пояс.
- Публичный текст: `text` с серверными лимитами длины. Приватный текст и Telegram-привязки: `bytea` с AES-256-GCM, `key_id` и привязкой к контексту ресурса.
- Деньги: внутри Go целые `int64` в минимальных денежных единицах; в БД суммы расходов и долей зашифрованы. В JSON суммы передаются строками целых чисел, например `"amount_minor": "10000"`.
- Статусы: `text` с `CHECK`. Обязательные поля имеют `NOT NULL`, связи имеют явное поведение удаления.
- `jsonb` применяется для небольших payload уведомлений и параметров интеграций; владельцы, участники и суммы остаются обычными колонками.
- У изменяемых пользователем заметок и расходов есть `version` для проверки конкурентного редактирования.

Выбор опирается на стандартные [типы PostgreSQL](https://www.postgresql.org/docs/17/datatype.html) и [ограничения целостности](https://www.postgresql.org/docs/18/ddl-constraints.html). Проверки между несколькими строками выполняются транзакцией; обычный `CHECK` не заменяет проверку суммы всех долей расхода.

Шифрование, хэши и хранение ключей обязательны по [модели безопасности](10-security.md). SQL обеспечивает связи и уникальность, а расшифровка, проверки сумм и доступ к содержимому выполняются сервисом внутри разрешённой операции.

## Аккаунт и интеграции

| Таблица | Основные данные и ограничения |
| --- | --- |
| `users` | `id`, уникальный `telegram_id_lookup`, зашифрованный Telegram ID, выбранное публичное имя, username, статус аккаунта |
| `user_settings` | Один ряд на пользователя: язык, тема, timezone, закреплённые приложения |
| `sessions` | Уникальный хэш токена, `user_id`, `expires_at`; исходный токен не хранится |
| `app_links` | `user_id`, `app_id`, подтверждённый внешний ID; уникальная пара пользователя и приложения |
| `integration_requests` | Идемпотентный ключ, автор, источник, цель, хэш подтверждённого содержимого, результат |

Каталог четырёх приложений задаётся конфигурацией, отдельная БД магазина приложений не нужна. Внешние ID Docgen и SruDay не являются внешними ключами в их базы и не дают права доступа без проверки соответствующим сервисом.

## Лента и сообщества

| Таблица | Назначение |
| --- | --- |
| `social_posts` | Автор, текст, аудитория, необязательное сообщество, время публикации |
| `social_comments` | Пост, автор и текст комментария |
| `social_reactions` | Уникальная реакция пользователя на выбранный пост или комментарий |
| `social_follows` | Уникальная пара подписчика и автора; взаимная подписка отображается как дружба |
| `social_post_views` | Уникальная пара `(post_id,user_id)`, без IP и данных устройств; собственные просмотры автора исключаются |
| `social_communities` | Зашифрованное название закрытого сообщества, владелец, состояние и хэш отзываемого приглашения |
| `social_members` | Уникальное участие пользователя, роль и состояние членства |
| `social_blocks` | Направленная блокировка пары пользователей |
| `social_reports`, `social_moderation_actions` | Жалобы, решения и ограниченный журнал действий модератора |

Текст закрытых публикаций, их комментариев и приватные материалы жалоб хранятся зашифрованными. Для публичного и закрытого текста используются взаимоисключающие поля с проверкой аудитории; открытая копия приватного текста не сохраняется для поиска или превью.

Лента строится при чтении из доступных постов подписок и сообществ с сортировкой по `id DESC`. Страницы используют курсор `before` по ID. Новые публикации появляются при обновлении начала ленты. Индивидуальная материализованная лента пока не нужна.

Подписка не даёт доступ к закрытому сообществу или календарю SruDay. Удалённые и недоступные публикации не возвращаются ни напрямую, ни через комментарии и реакции.

## SruNotes

`notes` хранит владельца, зашифрованные заголовок и текст, `key_id`, `version` и время изменения. `note_grants` хранит получателя, автора разрешения, состояние и необязательный контекст выдачи через сообщество.

Доступ на чтение есть у автора или у действующего получателя. При выдаче группе сохраняется выбранный состав получателей; новых участников автоматически не добавляем. Для разрешения через группу дополнительно проверяется текущее членство. Выход отзывает такие разрешения; повторное вступление само их не восстанавливает. Отдельно выданное личное разрешение сохраняется до отзыва автором.

Карточка хранит ID заметки, а не копию её текста. Каждый просмотр заметки и превью проверяет права заново. После отзыва, удаления заметки или выхода из выбранной группы сервер перестаёт возвращать содержимое, клиент сбрасывает связанный кэш при сверке доступа. Уже прочитанный или скопированный человеком текст отозвать невозможно.

Редактирует только владелец. Проверка `version` предотвращает молчаливую перезапись более новой версии. История совместного редактирования в первую модель не входит.

## SruSplit

| Таблица | Назначение |
| --- | --- |
| `split_groups` | Зашифрованное название, владелец и валюта `KZT` |
| `split_members` | Уникальный участник группы и состояние участия |
| `split_expenses` | Группа, автор, плательщик, зашифрованные описание и сумма, `key_id`, `client_request_id`, `version` |
| `split_shares` | Уникальная доля участника в расходе, зашифрованная сумма в минимальных единицах, `key_id` |

Плательщик и участники долей должны принадлежать одной группе. Межтабличные связи закрепляются составными внешними ключами там, где это возможно. Перевод в неактивное участие не удаляет исторические доли и не изменяет ранее рассчитанные суммы.

Для `amount_minor = A` и `N` участников вычисляем целые `q = A / N` и `r = A % N`. Все получают долю `q`, первые `r` участников в стабильном порядке по ID получают дополнительно одну минимальную единицу. Группа, расход и доли изменяются в одной транзакции; сумма долей проверяется перед commit.

Положительность расхода, неотрицательность долей и пределы диапазона проверяет Go-сервис до шифрования. Для баланса он читает доступные строки группы, расшифровывает суммы и складывает целые числа. SQL `SUM` по ciphertext не применяется. Ошибка расшифровки прекращает расчёт, а не превращается в нулевую сумму.

Для 100,00 тенге на троих: `10000 = 3334 + 3333 + 3333`. Баланс участника равен сумме оплаченного им минус сумму его долей. Сумма балансов всех участников группы равна нулю. Балансы рассчитываются из расходов и долей, отдельный редактируемый «кошелёк» не создаётся.

Итоги считаются по согласованному снимку всей группы, а не только по загруженной странице расходов. Для нескольких чтений нужен подходящий уровень изоляции, например REPEATABLE READ. Стоимость расшифровки и расчёта всей истории проверяем на пилотных объёмах, без сохранения открытых сумм ради ускорения.

Повтор создания расхода защищён уникальным ключом автора и `client_request_id`. Правка атомарно заменяет доли и увеличивает `version`; при конфликте возвращается актуальная версия. Ввод суммы проверяется без преобразования через float, с ограничением диапазона и количества знаков после запятой.

## SruPulse

`pulse_statuses` хранит автора, зашифрованный текст, `key_id`, `expires_at` и состояние завершения. `pulse_audience` задаёт выбранных пользователей или сообщество. `pulse_responses` содержит уникальную пару статуса и откликнувшегося пользователя.

Доступность проверяется по аудитории, блокировкам и текущему времени сервера. При отклике статус блокируется и повторно проверяется в транзакции. Истечение срока и ручное завершение запрещают новые отклики, даже если фоновая очистка ещё не выполнялась. Календарь не копируется в эти таблицы.

## Уведомления и входящие updates

`notification_preferences` хранит категории и mute. `bot_destinations` хранит проверенную привязку к нужному боту, зашифрованный личный chat ID и состояние разрешения писать. `bot_updates` содержит уникальную пару `(bot_id, update_id)` и отметку обработки, без полного исходного сообщения Telegram.

`notification_delivery` одновременно является outbox и очередью отправки: получатель, тип события, ссылка на ресурс, минимальный payload, уникальный dedupe key, состояние, число попыток, `next_attempt_at`, lease и Telegram message ID. Отдельная универсальная система очередей не требуется. Правила доставки находятся в [отдельном документе](08-bot-notifications.md).

## Основные индексы

| Запрос | Индекс или ограничение |
| --- | --- |
| Найти пользователя или сессию | UNIQUE `users(telegram_id_lookup)`, UNIQUE `sessions(token_hash)` |
| Посты автора или сообщества | `(author_id, created_at DESC, id DESC)` и `(community_id, created_at DESC, id DESC)` |
| Мои и доступные заметки | `notes(owner_id, updated_at DESC, id DESC)`, `note_grants(recipient_id, note_id)` |
| Расходы и доли | `split_expenses(group_id, created_at, id)`, UNIQUE `split_shares(expense_id, user_id)` |
| Отклики | UNIQUE `pulse_responses(status_id, user_id)` |
| Очередь Telegram | `(next_attempt_at, id)` для ожидающих заданий, отдельный путь поиска просроченного lease |

Внешним ключам добавляются индексы, необходимые для обратных выборок и удаления. Первичный или уникальный индекс повторно не дублируется. План проверяется на реальных запросах через `EXPLAIN ANALYZE`, без индексов «на всякий случай».

## Миграции, удаление и восстановление

Миграции применяет отдельная команда. Для совместимого выпуска сначала добавляются новые поля и код их поддержки, затем отдельным изменением убирается устаревшее. Старые базы Docgen и SruDay имеют собственные миграции и резервные копии.

Сроки хранения переписки, модерационных записей и расходов определяются до публичного запуска. Удаление аккаунта не должно случайным cascade разрушать общие расходы других участников. Выбираем явное удаление личных данных и обезличивание сохраняемых совместных записей согласно утверждённым правилам.

До production нужен автоматический backup вне сервера приложения и проверенный restore. Для managed БД проверяется наличие и срок PITR, для самостоятельной нужны настроенные архивирование и расписание резервирования. Подходы описаны в [документации PostgreSQL](https://www.postgresql.org/docs/18/backup.html); конкретные RPO и RTO фиксируются после выбора хостинга и проверки восстановления.
