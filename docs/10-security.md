# Безопасность и защита данных

Статус: обязательные требования к будущей реализации. Документ не означает, что защита уже реализована или проверена на работающем сервисе.

## Что защищаем

Защищаем личную переписку, заметки, расходы, закрытые публикации, Telegram-привязки, документы и секреты сервисов. Основные риски: доступ к чужому объекту по ID, утечка дампа или бэкапа, XSS, кража сессии, чрезмерные права оператора, поддельный webhook и случайная публикация секретов.

Модель включает несколько независимых уровней: серверная авторизация, шифрование транспорта, шифрование чувствительных полей, хэши проверочных секретов, ограничение доступа к инфраструктуре и проверенное восстановление. Основа правил доступа следует [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## Хэширование и шифрование

| Данные | Как храним | Зачем |
| --- | --- | --- |
| Токены сессий, одноразовые коды интеграций и токены приглашений | SHA-256 от случайного секрета не менее 32 байт; исходный секрет выдаётся однократно | Сервер проверяет предъявленный секрет, не восстанавливая его из БД |
| Поисковый индекс Telegram ID | HMAC-SHA-256 с отдельным серверным ключом | Поиск аккаунта без открытого Telegram ID и без перебираемого обычного SHA от числового ID |
| Сам Telegram ID и chat ID доставки | AES-256-GCM, ключ вне БД | Сервер может выполнить интеграцию или отправить уведомление |
| Текст сообщений, заголовки и содержимое заметок, названия закрытых групп и диалогов | AES-256-GCM на уровне приложения | Один дамп БД не раскрывает приватный текст |
| Закрытые публикации и статусы SruPulse | AES-256-GCM на уровне приложения | Защита текста, предназначенного ограниченной аудитории |
| Описание и суммы расходов, суммы долей | AES-256-GCM на уровне приложения | Финансовое содержимое не раскрывается одним SQL-дампом |
| Публично выбранные имя, описание профиля и общие посты | Обычные поля с контролем аудитории | Эти данные предназначены для отображения аудитории SruNal |
| Диски БД, файловое хранилище и резервные копии | Шифрование средствами хостинга и отдельная защита backup | Защита носителей и скопированных архивов |

SHA-256 применяется к высокоэнтропийным случайным токенам, а не к коротким паролям. Новая система паролей не создаётся, вход выполняется через Telegram. Пароли операторов и текущая защита DocGen относятся к отдельной проверке существующего сервиса.

Временные значения и UUID идемпотентности не используются как токены доступа. ID объекта не является секретом и не заменяет проверку прав.

## Шифрование полей

Используем стандартные `crypto/aes`, `crypto/cipher` и `crypto/rand` Go. Предпочтителен `NewGCMWithRandomNonce` в поддерживаемой версии Go, чтобы генерация nonce выполнялась стандартной библиотекой. Учитываем ограничения числа шифрований одним ключом и ротируем ключ до их достижения. Формат и API проверяются по [документации Go](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce); выбор authenticated encryption соответствует [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).

Запись содержит `key_id` и `ciphertext`; случайный nonce включён в запечатанный payload. Дополнительные аутентифицируемые данные связывают ciphertext с назначением поля, типом ресурса, его неизменным ID и владельцем. Идентификатор ресурса выделяется внутри транзакции до запечатывания. Копирование ciphertext в другой контекст не должно приводить к успешной расшифровке.

Перед расшифровкой сервер проверяет право на ресурс. Суммы SruSplit расшифровываются в сервисе после проверки участия и обрабатываются как целые числа. Доли, проверка общей суммы и баланс вычисляются в Go; база хранит связи, уникальность и зашифрованные значения. Расшифрованные суммы в БД не дублируются.

Отсутствующий ключ, неизвестный `key_id`, ошибка генерации случайности или проверки тега являются ошибкой. Сервис не сохраняет открытый текст как fallback и не выдаёт повреждённые данные. SQL-поиск по тексту приватных заметок и сообщений не добавляется в первую версию, поскольку не должен требовать незашифрованной копии.

## Ключи и секреты

Ключи шифрования, HMAC-индекса, Bot API, webhook и служебных интеграций независимы. Для production получаем их из secret manager/KMS или из защищённых файлов секретов, подключённых к нужному процессу вне образа и репозитория. В разработке разрешены локальные игнорируемые значения, не используемые в production.

Внутри шифрования разделяем ключи содержимого, Telegram-личности и назначения доставки. Worker получает только ключ chat ID доставки и ограниченную роль БД с нужными метаданными и очередью, без доступа к ciphertext переписки и заметок. Это не один общий ключ, скопированный во все процессы.

В PostgreSQL находятся только `key_id`, ciphertext, хэши и служебные метаданные. Ключи не хранятся рядом с SQL-дампом, в Docker image, `VITE_*`, клиентском бандле или журнале CI. Worker получает только секреты, необходимые для доставки и чтения нужных ему полей.

При ротации новые записи используют новый ключ, старые читаются по `key_id`, а фоновая процедура постепенно перешифровывает данные. Старый ключ нельзя удалять до завершения миграции и окончания срока бэкапов, для которых он необходим. Ротация HMAC-индекса Telegram ID требует отдельного перестроения индекса с поддержкой переходного поиска и без создания дублирующих аккаунтов.

Копия ключей для восстановления хранится отдельно и с ограниченным доступом. Потеря ключа делает зашифрованные данные невосстановимыми. Компрометация сервера вместе с доступными ему ключами требует отзыва секретов, расследования и ограничения доступа; одно шифрование диска этот риск не закрывает.

## Авторизация

- Любой новый маршрут требует аутентификации и явного правила доступа, кроме минимального списка health, входа и webhook.
- Личный объект выбирается запросом с ограничением владельца, участника или действующего разрешения. Подстановка чужого ID не должна менять результат этой проверки.
- Превью карточки, скачивание, экспорт, поиск, SSE и отправка уведомления проходят те же правила, что основной экран.
- Роль оператора SruDoc не даёт права на переписку, заметки или расходы. Модератор сообщества получает только свой контекст и отдельно разрешённые материалы жалобы.
- Отзыв доступа и выход из группы учитываются до выдачи содержимого и его расшифровки. Серверный или клиентский кэш не является основанием для прежнего разрешения.
- Внешние сервисы получают минимальный DTO для конкретного подтверждённого действия. Токены другого приложения не используются как общая сессия.

Для проверки приватного объекта возвращается нейтральное состояние недоступности, без раскрытия его содержимого и владельца постороннему. В журнале аудита сохраняются субъект, действие, ресурс и результат, но не приватный текст.

## Сессии и Telegram

`initData` проверяется на сервере: подпись разрешённого бота, корректный пользователь, свежесть `auth_date` и допустимое отклонение времени. Имя, `initDataUnsafe` и `startapp` не являются доказательством личности. Начальные пределы свежести и TTL сессии задаются явно в конфигурации и проверяются тестами; бессрочных сессий нет.

Сессионный токен генерируется через `crypto/rand`, хранится у клиента только в памяти и передаётся в bearer-заголовке по HTTPS. В БД находится его хэш. Выход отзывает сессию, блокировка аккаунта запрещает все его сессии и новые входы. Управление сессиями рассматривает токен как полноценный секрет согласно [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Webhook использует отдельный проверяемый secret header и идемпотентный `update_id`. Бот пишет только в подтверждённый личный чат с разрешением. Уведомление не включает приватный текст по умолчанию, а кнопка не обходит авторизацию в Mini App.

## Фронтенд и API

Пользовательские сообщения и заметки отображаются как текст React. `dangerouslySetInnerHTML`, исполнение пользовательского HTML и загрузка произвольных скриптов для этих сценариев не нужны. Ссылки принимают только разрешённые схемы; HTML и Markdown сообщений бота формируются безопасными серверными шаблонами.

CSP разрешает только нужные источники скриптов, подключения и шрифтов. Telegram SDK остаётся явным разрешённым источником. Выбранные шрифты и иконки по возможности размещаем самостоятельно с сохранением лицензий. Политика встраивания учитывает Telegram Web; слепое `frame-ancestors 'none'` или `X-Frame-Options: DENY` может сломать этот клиент и не принимается без проверки.

API работает с одним origin. Не разрешаем произвольный CORS origin. Bearer-сессия не отправляется браузером автоматически как cookie; если появится cookie-вход, для него отдельно понадобятся CSRF-токен, проверка Origin и корректные Secure/HttpOnly/SameSite. Ошибки не возвращают SQL, stack trace, секреты или полный ответ внешнего сервиса.

Входные тела ограничиваются размером. Проверяются длины текста, формат ID, состав участников, диапазоны сумм и частота действий. SQL параметризуется. Сетевые обращения к интеграциям идут только на настроенные владельцем адреса; сервер не скачивает произвольные пользовательские URL и не открывает ими внутреннюю сеть.

На вход, сообщения, приглашения, отклики и интеграции действуют лимиты по IP и аккаунту. Аутентифицированный пользователь не получает неограниченную параллельную очередь или список всей базы. Размер страницы и число доступных одновременно соединений ограничены.

## Инфраструктура, логи и резервные копии

PostgreSQL доступен только сервисам и операторам с нужными правами. Приложение работает от роли без superuser, права миграций отделены. Контейнеры по возможности запускаются без root; секреты монтируются только для чтения, отладочные endpoint в production закрыты.

HTTPS используется снаружи, а соединение с managed БД проверяет сертификат TLS. В пределах одного сервера внутренняя сеть изолирована. Сетевой доступ к БД, backup и secret storage ограничивается отдельно.

Не логируем тела сообщений, заметки, суммы, `Authorization`, `initData`, секрет webhook и URL Bot API с токеном. SQL-параметры и запросы с приватным содержимым не выводятся в журналы. Мониторинг использует технические ID, счётчики и редактированные ошибки.

Архивы шифруются, хранятся вне сервера приложения с ограниченным доступом и сроком хранения. SQL-дамп не должен становиться общедоступным файлом в веб-каталоге или объектном bucket. Восстановление проверяется вместе с доступностью правильных версий ключей.

В CI нужны поиск секретов, `govulncheck` и проверка зависимостей npm, а также тесты прав и криптографического формата. Lock-файлы фиксируются. Предупреждение зависимости оценивается по достижимости и влиянию; обновление не должно слепо ломать приложение.

## Проверки до production

| Проверка | Ожидаемый результат |
| --- | --- |
| Чужие ID в API, превью, SSE и ссылках из бота | Нет приватных данных |
| Отозванная сессия, неверная подпись, устаревший вход | Доступ отклонён |
| SQL-дамп без серверных ключей | Нет исходных токенов, Telegram ID, приватных текстов и сумм расходов |
| Изменённый ciphertext, AAD или неизвестный ключ | Контролируемая ошибка, без plaintext fallback |
| Ротация ключей и восстановление backup | Старые и новые записи читаются только нужными ключами |
| Выход из группы и отзыв заметки | Закрыты основной ответ, превью и новые уведомления |
| XSS-строка и небезопасная ссылка | Отображаются безопасно или отклоняются |
| Поддельный и повторный webhook | Не создаёт действие и повторную доставку |
| Проверка сборки, логов и репозитория | Нет секретов и приватных payload |

## Пределы защиты

Это серверное шифрование, а не E2EE: сервер должен уметь показывать разрешённые данные и выполнять расчёты. Публичные данные и технические связи между объектами могут быть видны в дампе. Пользователь может скопировать уже полученный текст, а взлом его устройства или сервера с ключами требует отдельного реагирования.

Защита новых модулей не доказывает безопасность существующего DocGen и SruDay. Перед общим production-запуском проверяем их права, секреты, файлы и интеграционные маршруты отдельно. Реализованные гарантии подтверждаются тестами и проверкой инфраструктуры, а не наличием документа.
