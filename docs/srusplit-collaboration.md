# SruSplit: совместные чеки, возвраты и напоминания

Актуальная реализация от 14 ноября 2026 года. При расхождениях с ранними промптами этот документ имеет приоритет. Валюта KZT, суммы в API передаются строками целых минимальных единиц. Расчёты выполняет Go, OCR заполняет только проверяемый черновик.

## Путь пользователя

1. В группе нажать «Добавить чек». Выбрать JPEG, PNG или WebP до 20 МиБ либо начать ручной ввод.
2. При необходимости выделить прямоугольную область, повернуть фото на 90° и применить изменения. Рамку можно настроить ползунками. «Без изменений» возвращает исходник. Без применения изменённой рамки отправка заблокирована.
3. Разрешить передачу выбранного изображения DeepSeek. Редактор работает в браузере, учитывает EXIF и экспортирует JPEG с качеством 0,92 и стороной до 4096 px. Сервер сохраняет свои ограничения формата, количества пикселей и одновременных обработок.
4. Проверить названия, цены, количества, скидку и обслуживание. Сверить итог. Подтвердить предложения комбо, если они верны. OCR не связывает строки автоматически только по нулевой цене.
5. Открыть выбор покупок и поделиться ссылкой. Обычный товар распределяется по количеству, позиция «Общее» делится поровну между выбравшими её. Добавки комбо наследуют доли основной позиции, их количество и стоимость сохраняются.
6. Автор проверяет распределение, указывает плательщика и отправляет чек на подтверждение. Автор подтверждает своей отправкой; плательщик и все остальные участники распределения должны ответить отдельно, включая получивших бесплатную добавку.
7. Последнее согласие создаёт один расход и долги неплательщиков одной транзакцией. До этого чек не влияет на баланс и отчёт. Вопрос с пояснением блокирует завершение. Возврат к редактированию сбрасывает все согласия.

Чек имеет постоянный экран и доступен из списка чеков группы. Изменять состав может автор, участник меняет только собственный выбор. Поллинг раз в 5 секунд работает на открытом экране, при возвращении данные обновляются. Версия чека защищает от перезаписи чужого выбора.

### Состояния и доступ

`draft → collecting → review → saved`; автор может отменить незавершённый чек (`cancelled`) или вернуть его в `draft`. Сохранённый чек не редактируется. Старые расходы остаются учтёнными.

Приглашение использует 32 случайных байта, в БД хранится только SHA-256 токена. Срок ссылки 7 дней. Автор создаёт ссылки во время сбора выбора, автор или владелец группы отзывает их. Отмена чека также прекращает доступ по приглашению.

Вход по ссылке требует авторизации Telegram и отдельного нажатия «Вступить и выбрать покупки». До вступления показываются только сведения о приглашении, без позиций и расходов. После вступления человек получает доступ ко всей истории группы. Это явно написано на экране: пересланную ссылку может использовать другой человек.

Пояснение к вопросу хранится зашифрованным и показывается автору чека и отправителю вопроса. Остальные видят статус ответа.

## Возвраты и расчёты

Отметка должника «Перевёл деньги» создаёт ожидающее погашение. Оно резервирует часть остатка, чтобы два параллельных запроса не создали переплату. Получатель нажимает «Получил деньги» либо «Не получил». Только подтверждённые возвраты меняют баланс. Получатель также может сам записать уже полученные деньги. Погашения старой версии считаются подтверждёнными.

Связанный с расходом долг не добавляет его сумму второй раз. Подтверждённый возврат по такому долгу уменьшает обязательство в общем балансе. Месячные расходы остаются суммой покупок, погашение не становится новой покупкой.

«Как рассчитаться» объединяет обязательства только между исходной парой людей. Например, встречные 4000 и 1500 ₸ дают взаимозачёт 1500 ₸ и перевод 2500 ₸ исходному кредитору. Получатель не заменяется третьим участником, абсолютный минимум переводов для всей группы не обещается.

Предложение само ничего не списывает. Обе стороны принимают расчёт, затем должник отмечает отправку, получатель подтверждает получение. При нулевой денежной части согласие второй стороны проводит только взаимозачёт. Погашения распределяются по исходным обязательствам от старых к новым. История сохраняет способ `offset` или `transfer`.

Финансовые изменения сериализуются блокировкой группы. Изменение обязательств делает прежнее предложение устаревшим. Уже учтённый возврат или подтверждённый расчёт нельзя записать вторым повторным запросом. Ключ запроса с другим содержимым отклоняется.

## Напоминания и бот

Любая сторона долга предлагает дату и частоту. Другая принимает или предлагает новые условия. По умолчанию выбрана неделя; доступны 1, 3 и 7 дней. Срок и уведомления привязаны к 18:00 в часовом поясе должника, пояс фиксируется при согласовании. Новое предложение приостанавливает прежние напоминания до нового согласия.

До согласия автоматических напоминаний нет. Ожидающий возврат приостанавливает их, полное погашение отключает. Любая сторона может отключить напоминания. Пропущенные периоды не воспроизводятся пачкой: создаётся одно актуальное задание, следующий срок переносится в будущее с сохранением местного времени.

В разделе долгов пользователь разрешает боту писать через нативный `requestWriteAccess`. Отказ не блокирует расчёты. Отдельно можно отключить уведомления об изменениях долгов и скрыть суммы. Сервер хранит предпочтение пользователя, фактическую возможность доставки контролирует Telegram.

Планировщик API раз в минуту читает согласованные сроки, проверяет остаток и создаёт зашифрованное задание. Worker получает только ключ доставки и ключ идентификации, не ключ контента. Перед отправкой он проверяет текущие настройки, версию долга, актуальность соглашения и отсутствие ожидающего возврата. Суммы скрываются и при изменении настройки после постановки сообщения в очередь.

Задания выдаются атомарно через `FOR UPDATE SKIP LOCKED` с токеном владения и арендой на 10 минут. Просроченный обработчик не может отправить или изменить задание нового владельца. Ограничение Bot API `retry_after` учитывается. После неоднозначного сетевого сбоя повтор сообщения всё ещё возможен, строгая однократная доставка не гарантируется.

## API и данные

Все маршруты ниже находятся под `/api/v1/split` и требуют сессии. Проверки членства и ролей выполняются сервером.

| Маршрут | Назначение |
| --- | --- |
| `GET /groups/{id}/receipts` | Последние 100 чеков группы; экран конкретного чека доступен по ID |
| `GET/PATCH /receipts/{id}` | Чек, стабильные ID позиций; изменение требует `version` |
| `POST /receipts/{id}/collect` | Открыть сбор выбора |
| `POST /receipts/{id}/claim` | Свой выбор: `version`, `item_id`, `count`; ноль снимает выбор |
| `POST /receipts/{id}/submit` | Зафиксировать распределение: версия, плательщик, ключ запроса, описание, категория |
| `POST /receipts/{id}/respond` | `accepted` либо `question` с пояснением и версией |
| `POST /receipts/{id}/reopen`, `/cancel` | Действия автора с версией |
| `POST /receipts/{id}/invite`, `/revoke-invites` | Создание и отзыв приглашений |
| `GET /invites/{token}`, `POST /invites/{token}/join` | Предпросмотр приглашения и явное вступление |
| `POST /debts/{id}/payments` | Возврат с ключом запроса; должник создаёт `pending`, кредитор `confirmed` |
| `POST /debts/{id}/payments/{paymentId}/respond` | Ответ кредитора: `accept: true/false` |
| `GET/POST /groups/{id}/settlements` | План и создание предложения с `other_id`, `group_version`, ключом запроса |
| `POST /settlements/{id}/respond` | `agree`, `report`, `confirm`, `reject` |
| `GET/POST /debts/{id}/reminder` | Условия; `propose` с версией, датой `YYYY-MM-DD`, `interval_days`; `accept` или `disable` с версией |
| `GET/POST /bot-access` | Свои настройки: `opt_in`, `enabled`, `show_amounts` |

У позиции есть `allocation_mode: units/shared` и необязательная `parent_position`, индекс основной позиции в текущем чеке. Вложенные комбо и ссылки на другой чек запрещены. `suggested_parent_position` от OCR не влияет на расчёт до подтверждения автором.

Старый `/receipts/{id}/save` не обходит согласования. Устаревший клиент получает ошибку и должен заново открыть приложение. Неверная версия возвращает 409, актуальные данные перечитываются.

Новые фото не записываются в БД, временные файлы, очередь или резервные копии. В БД остаются зашифрованные распознанные данные. Старые сохранённые фотографии обслуживаются прежней политикой удаления. Ключ DeepSeek существует только в серверном окружении, исходные фото и ключ не включаются в Git и frontend.

## Запуск и обновление

Нужны миграции `000016` - `000020` поверх предыдущих. Они добавляют версии и комбо, подтверждения и приглашения, статусы возвратов, предложения расчётов, договорённости о напоминаниях и аренду доставки.

1. Сделать резервную копию БД, остановить старые API и worker.
2. Выполнить `go run ./cmd/migrate -dir ../db/migrations` из `backend` либо сервис Compose `migrate`. Для мигратора достаточно `SRUNAL_DATABASE_URL`.
3. Запустить новый API. При первом запуске он переносит старые Telegram ID с ключа контента на ключ идентификации, без промежуточной записи открытых ID. Перенос идемпотентен, новая авторизация также обновляет шифрование идентификатора.
4. Запустить worker и обновлённый frontend вместе. Не оставлять старые API параллельно с новой версией шифрования идентификаторов.

Дополнительно настроить публичное `SRUNAL_BOT_USERNAME`, без `@`, и при необходимости `SRUNAL_MINIAPP_NAME`. Без имени бота ссылки недоступны; worker не отправляет невалидные относительные URL как кнопки. Deep links открывают чек или раздел долгов после обычной проверки сессии и прав.

API использует `SRUNAL_CONTENT_KEY`, `SRUNAL_IDENTITY_KEY`, `SRUNAL_DELIVERY_KEY`, `SRUNAL_HMAC_INDEX_KEY`. Worker использует `SRUNAL_IDENTITY_KEY`, `SRUNAL_DELIVERY_KEY`, `SRUNAL_BOT_TOKEN`, БД и публичные настройки ссылки. Compose передаёт эти значения отдельно. Ключи нельзя заменять при обычном обновлении. Откат к коду до разделения ключей идентификации требует отдельного обратного переноса идентификаторов.

Проверки: `go test ./...`, `go vet ./...`, `npm run build`, Node-тесты `photo.test.ts` и `receiptPreview.test.ts`. Для интеграционных тестов задать `SRUNAL_TEST_DATABASE_URL` на отдельную тестовую БД: тесты создают и удаляют собственные схемы.

Проверены гонки выбора и возвратов, согласование тремя пользователями, бесплатные добавки, повторные запросы, взаимозачёт, устаревшие расчёты, пауза напоминаний, DST, два worker и разделение ключей. Доставку Bot API проверяем подменным отправителем; реальным пользователям тестовые сообщения не отправляются.

Технические источники: [Telegram Mini Apps](https://core.telegram.org/bots/webapps), [Canvas toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob), [блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).
