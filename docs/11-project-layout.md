# Разделение super app по папкам и файлам

## Основное правило

**Одно приложение имеет свою папку на фронтенде и свою папку на бэкенде.** Внутри лежат его экраны, типы, запросы, правила и тесты. Разработчик открывает папку приложения и видит весь относящийся к нему код.

SruNal сохраняет одну сборку React, один Go-модуль и общую PostgreSQL для новых данных. Разделение папок не создаёт отдельный сервер, пакет npm или `go.mod` для каждого приложения. Docgen и SruDay подключаются к существующим сервисам через принадлежащие им адаптеры.

## Где находится каждое приложение

| Приложение | React | Go | Экран |
| --- | --- | --- | --- |
| Docgen | `web/src/apps/doc/` | `backend/internal/apps/doc/` | `/apps/doc` |
| Календарь SruDay, основной раздел | `web/src/apps/day/` | `backend/internal/apps/day/` | `/calendar` |
| SruPulse | `web/src/apps/pulse/` | `backend/internal/apps/pulse/` | `/apps/pulse` |
| SruNotes | `web/src/apps/notes/` | `backend/internal/apps/notes/` | `/apps/notes` |
| SruSplit | `web/src/apps/split/` | `backend/internal/apps/split/` | `/apps/split` |

Лента и профиль самой SruNal находятся в `web/src/core/`. Общие серверные возможности расположены в `backend/internal/core/`: `auth`, `user`, `social`, `notify`.

## Пример фронтенда SruNotes

```text
web/src/apps/notes/
  routes.tsx                 точка подключения экранов заметок
  api.ts                     запросы, query keys и обновление данных заметок
  types.ts                   типы API и модели интерфейса заметок
  pages/
    NotesPage.tsx            мои и доступные мне заметки
    NotePage.tsx             чтение и редактирование заметки
    NotePage.test.tsx         проверки поведения экрана
  components/
    NoteCard.tsx              карточка в списке заметок
    ShareNoteSheet.tsx        выбор получателей и отзыв доступа
```

`routes.tsx` является точкой подключения приложения к общему роутеру. Остальные файлы используются внутри `apps/notes`. `api.ts` вызывает общий HTTP-клиент, но знает только контракты заметок. Query keys начинаются с `notes`, чтобы обновление заметки не сбрасывало данные других приложений.

`NoteCard` принадлежит SruNotes. Базовые `Card`, `Sheet`, поля и состояния берутся из `shared/ui`, где сохранён стиль DocGen. Общие компоненты не импортируют типы заметок, расходов или заказов.

Тема, язык, сессия и Telegram SDK создаются на уровне SruNal. Внутри приложения не появляется второй роутер, второй обработчик темы или собственная авторизация.

Пример показывает назначение файлов, а не обязательное число файлов. Маленький экран может начинаться одним компонентом. Дополнительные подпапки и отдельный `index.ts` для каждой директории заранее не создаются.

## Пример бэкенда SruNotes

```text
backend/internal/apps/notes/
  http.go                    маршруты, разбор запроса, HTTP-ответ
  service.go                 правила заметок, доступ и операции
  store.go                   SQL только таблиц notes и note_grants
  types.go                   типы заметки и разрешения
  service_test.go            правила, права автора и получателя
  store_test.go              SQL и транзакции на тестовой PostgreSQL
```

Пакет называется `notes`. Обработчик передаёт проверенный контекст пользователя сервису. Сервис проверяет правила, использует `store.go` для запросов с ограничением доступа и `platform/secure` для шифрования. SQL-код приложения не разбрасывается по общей папке всех репозиториев.

Точка подключения пакета экспортирует регистрацию HTTP-маршрутов и конструктор сервиса. Для интеграций экспортируются только необходимые методы, например разрешённое чтение заметки или выдача доступа. Внутренний store не становится публичным API для других приложений.

Для SruSplit аналогично рядом находятся HTTP, расчёт долей, работа с расходами и тесты. Дополнительный файл `balance.go` появляется, если расчёт уже удобнее читать отдельно от сервиса. Его не переносят в общий `utils`.

## Docgen и SruDay

Их серверные папки сначала содержат `client.go` для доверенного API, `service.go`, `http.go` и нужные типы. Логика генерации, старый календарь и SQL существующих проектов остаются у соответствующих сервисов.

Клиент DocGen находится в `apps/doc/client.go`, клиент SruDay в `apps/day/client.go`. Папка `integration` отвечает за пользовательские действия между приложениями, а не становится общим складом этих клиентов.

## Общий код и зависимости

| Папка | Что в ней находится | Чего в ней не должно быть |
| --- | --- | --- |
| `web/src/app` | Общий роутер, провайдеры, реестр приложений, lazy import | Экраны и правила заметок или расходов |
| `web/src/core` | Лента и профиль SruNal | Отдельные приложения каталога |
| `web/src/shared` | UI DocGen, HTTP-клиент, Telegram SDK, локализация | Зависимости от конкретного приложения |
| `backend/internal/app` | Создание сервисов и подключение маршрутов | Бизнес-правила |
| `backend/internal/core` | Авторизация, аккаунт, соцсеть, уведомления | SQL и расчёты отдельных приложений |
| `backend/internal/apps` | Модули четырёх приложений каталога и основного календаря | Прямые обращения к данным соседнего приложения |
| `backend/internal/integration` | Согласованные действия между публичными сервисами | Обход проверки доступа и прямой SQL чужого store |
| `backend/internal/platform` | HTTP, БД, криптография, транспорт Bot API, конфигурация | Знание о заметках, заказах и долях расходов |

Правила импортов:

1. Фронтенд приложения использует собственные файлы и общий `shared`. Переход в другое приложение выполняется через маршрут SruNal.
2. React-модули соцсети не импортируют внутренние компоненты приложений. Карточка ресурса содержит `app_id` и ID объекта; содержимое и разрешения определяет API владельца.
3. Go-приложения используют `platform` и необходимые публичные функции `core`, например контекст авторизации и постановку уведомления. `core` не импортирует `apps`.
4. Прямые импорты между `apps/notes`, `apps/split` и другими приложениями запрещены. Их публичные сервисы соединяет `integration`, зависимости передаются конструкторами.
5. `platform` не импортирует `core`, `apps` или `integration`. Общая сборка в `internal/app` может подключать все нужные модули.

Например, подтверждённую публикацию карточки заметки собирает `integration`: сервис заметок проверяет доступ и получателей, социальный сервис сохраняет разрешённую публикацию. Для внешних Docgen и SruDay используются отдельные подтверждённые запросы, без общей транзакции через две БД. Ограничение идемпотентности внешнего календаря описано в [документации SruDay](sruday-integration.md).

## Таблицы и миграции

Схема остаётся описанной в [модели данных](07-data-model.md). У модуля есть владелец таблиц: `notes` и `note_grants` относятся к SruNotes, `split_*` к SruSplit, `pulse_*` к SruPulse. Чужой модуль получает данные через сервис владельца. Общие таблицы аккаунтов и разрешённые внешние ключи не создают отдельные копии пользователей на каждое приложение.

SQL-миграции сохраняем в **одном последовательном каталоге** `db/migrations/`; их применяет `cmd/migrate`. Имя файла обозначает владельца изменения:

```text
db/migrations/
  000001_core_identity.up.sql
  000002_social_chat.up.sql
  000003_chat.up.sql              историческая миграция, не активный модуль
  000005_notes.up.sql
  000006_split.up.sql
  000007_pulse.up.sql
  000011_chat_attachments.up.sql  историческая миграция
  000012_social_views.up.sql
```

Порядок миграций уже зафиксирован в репозитории; файл `.down.sql` сопровождает соответствующий `.up.sql`. Старые миграции переписки сохраняются для совместимости, без действующих `core/chat` и API сообщений. Их наличие не является указанием удалять исторические таблицы. Независимые журналы миграций внутри приложений одной БД не создаются. Существующие базы Docgen и SruDay сохраняют свои миграции.

## Как добавить или изменить приложение

1. Найти его папки в `web/src/apps/<id>` и `backend/internal/apps/<id>`.
2. Добавить экран, запрос и серверное правило рядом с остальным кодом этого приложения.
3. Подключить маршруты и метаданные через `web/src/app` и `backend/internal/app`.
4. При изменении хранения добавить SQL-миграцию с именем приложения в общий журнал.
5. Для взаимодействия с другим приложением добавить конкретное действие в `integration`, сохранив проверки прав владельцев.
6. Добавить проверки рядом с изменённым кодом и проверить маршрут из каталога и переход из уведомления.

Новый общий компонент выносится в `shared/ui`, когда он действительно одинаков для нескольких экранов. Бизнес-правило остаётся у своего приложения. Пустые папки, отдельные сборки и универсальная система плагинов для этого разделения не нужны.

Документ описывает будущую организацию кода. Сам код и папки приложений этим изменением не создаются.
