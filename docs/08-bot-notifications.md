# Уведомления в чате Telegram-бота

## Канал доставки

По требованию пользователя внешние уведомления SruNal приходят **в личный чат Telegram-бота**. В Mini App работают лента, календарь и приложения; бот сообщает о важных изменениях и даёт кнопку перехода к нужному экрану. Web Push и постоянная работа WebView для этого не требуются.

На старте пользователь открывает диалог с ботом или разрешает ему писать через [`requestWriteAccess`](https://core.telegram.org/bots/webapps#initializing-mini-apps). В серверной привязке сохраняются проверенный пользователь, нужный бот, личный chat ID и состояние доступа. Номер телефона и Telegram username для этой привязки не нужны.

Личный chat ID хранится зашифрованным, ключ назначения доставки находится вне БД. В заданиях хранятся ссылки на ресурс и получателя, без копии приватной заметки или суммы. Worker получает доступ к настройкам и метаданным, необходимым для проверки отправки, и не требует ключа расшифровки приватного содержимого приложений.

Разрешение Telegram и настройки уведомлений являются разными проверками. Пользователь может разрешить сообщения боту и при этом отключить отдельные категории или отключить напоминания конкретного ресурса.

## События

| Источник | Когда уведомляем | Куда ведёт кнопка |
| --- | --- | --- |
| Лента SruNal | Комментарий к своему посту, если категория включена | Пост и обсуждение |
| SruPulse | Отклик на действующий статус | Статус и отклики |
| SruNotes | Автор предоставил получателю доступ к заметке | Доступная заметка |
| SruSplit | Добавлен или изменён общий расход, затрагивающий получателя | Группа расходов |
| Docgen | Документ готов, требуется действие по заказу | Экран заказа |
| SruDay | Поддерживаемое календарное уведомление после интеграции | Событие или день |

Самому автору действия уведомление не отправляется. Последние два источника подключаются после готовности доверенных API существующих сервисов; обработка напоминаний SruDay не считается уже реализованной. События внутренней переписки не создаются. Частые изменения одного ресурса могут объединяться в одно уведомление.

## Поток доставки

1. API проверяет права и выполняет пользовательское действие.
2. В той же транзакции сохраняет строки `notification_delivery` для нужных получателей.
3. После commit клиент получает результат, не ожидая Telegram.
4. Worker выбирает готовые задания, ставит lease и фиксирует захват.
5. Перед отправкой заново проверяет настройки, права получателя и актуальность ресурса. Отозванная заметка или завершённый статус могут больше не требовать уведомления.
6. Worker вызывает Bot API `sendMessage` и сохраняет результат либо план следующей попытки.

Outbox сохраняется вместе с действием, поэтому перезапуск API не теряет намерение уведомить. Идентификатор исходного события используется для dedupe key вида «источник + событие + получатель + категория». Повтор входящего события интеграции не создаёт новую доставку.

Worker захватывает строки через `FOR UPDATE SKIP LOCKED`, что позволяет обработчикам не ждать уже занятое задание. Это предусмотрено [синтаксисом PostgreSQL](https://www.postgresql.org/docs/18/sql-select.html). Транзакция захвата короткая: во время HTTPS-запроса в Telegram блокировка строки не удерживается.

Lease имеет владельца и срок, превышающий таймаут внешнего запроса. Завершение попытки обновляет только задание с тем же токеном lease. После аварии просроченное задание снова доступно обработчику.

## Ошибки и повторы

| Результат | Действие |
| --- | --- |
| Успех Bot API с `ok: true` | Сохранить Telegram message ID и состояние `sent` |
| Ограничение частоты | Планировать повтор не раньше `parameters.retry_after` |
| Временная серверная ошибка или сетевой сбой | Повтор с увеличивающейся задержкой и ограничением числа попыток |
| Бот заблокирован или право писать отозвано | Отключить доставку в этот чат до нового подтверждённого разрешения |
| Некорректный payload или разметка | Зафиксировать ошибку, не повторять бесконечно |
| Ресурс удалён, доступ отозван или уведомление уже неактуально | Пометить задание как пропущенное |

Структура результата описана в [Bot API](https://core.telegram.org/bots/api#making-requests), задержка при ограничении в [ResponseParameters](https://core.telegram.org/bots/api/types/responseparameters.md). Лимиты учитываются по боту и отдельному чату, а не бесконечным параллельным запуском запросов.

Гарантия системы: сохранение задания и повторяемая доставка с подавлением известных дублей. Если Telegram принял сообщение, но ответ потерялся, повтор может отправить ещё одно. Поэтому не обещаем exactly-once для внешних уведомлений и не изменяем расход или заказ в результате повторной доставки.

## Содержимое и переходы

Уведомление короткое: тип изменения и кнопка «Открыть». По умолчанию не включаем содержимое приватной заметки и суммы расходов. Предпросмотр содержимого можно вводить только как отдельную настройку после проверки аудитории.

Кнопка открывает зарегистрированный Mini App через `startapp`. Примеры маршрутов: публикация, календарь, заметка, группа расходов или заказ. Параметр определяет экран, но не даёт право чтения. После входа API заново проверяет пользователя; пересланная кнопка не открывает чужой приватный объект или документ.

Тексты формируются серверными шаблонами на языке получателя. Пользовательский текст не вставляется в Markdown или HTML без экранирования. API-токен бота хранится только на сервере; адреса запросов с токеном не логируются.

## Входящие сообщения боту

Production использует один webhook `POST /bot/webhook` на API. Проверяется HTTPS-доставка, ограничение размера запроса и заголовок `X-Telegram-Bot-Api-Secret-Token`. Секрет webhook независим от токена самого бота.

Пара `(bot_id, update_id)` обрабатывается идемпотентно. Изменение привязки и нужные задания фиксируются до успешного ответа webhook. Если БД недоступна, возвращается ошибка для повтора Telegram. Долгие внешние вызовы при приёме update не выполняются. Для начала достаточно `/start`, `/help` и URL-кнопки открытия приложения.

Токен бота уже используемого DocGen нельзя просто подключить ко второму обработчику. На каждый бот должен быть один владелец входящих updates. [Telegram не допускает `getUpdates` одновременно с настроенным webhook](https://core.telegram.org/bots/api/methods/setwebhook.md).

Пока старые сервисы самостоятельны, они сохраняют своих ботов и свою доставку. При объединении под одним ботом сначала переносим команды и обработку заказов в единый маршрут, затем переключаем приём updates. Событие получает одного владельца уведомления, чтобы пользователь не получал одновременно старую и новую отправку.

## Проверки реализации

- Действие и задание уведомления сохраняются вместе или откатываются вместе.
- Повтор события и update не создаёт новые задания.
- Перезапуск worker и просроченный lease не теряют ожидающую доставку.
- `retry_after` соблюдается, постоянные ошибки не повторяются бесконечно.
- Настройки категорий, блокировки и отзыв доступа учитываются перед отправкой.
- Уведомление приходит при закрытом Mini App и открывает правильный экран.
- Чужой пользователь по пересланной кнопке не получает приватные данные.

Это требования к доставке; наличие документа не означает, что включены все категории событий. Реализованный объём и конфигурация бота перечислены в [README](README.md).
